# MCP tool contract

The source of truth for tool names and arguments. The server (`src/server.ts`), the standing instructions and the README must all match this file.

Conventions:

- Tool args are snake_case. Every tool except `create_event` and `get_status` takes `event_id`.
- Money crosses the wire as dollar strings or numbers (`"26.88"`, `50`). The server parses them to integer cents exactly and returns both `*_cents` and a formatted `"$26.88"` string.
- `person` args accept a person id (`"maya"`), a name (`"Maya"`, case-insensitive), a phone number or an email address.
- People have a `phone`, an `email` or both. Fo texts people with a phone and emails people with only an email; `people`, `pending` and `messages` include each person's `channel` (`"text"` or `"email"`). Emails are matched case-insensitively and accept `"Name <addr>"` and `mailto:` forms; plus tags are kept, so `me+a@x.com` and `me+b@x.com` are different people.
- Every tool is idempotent: calling it twice with the same args leaves the same state.
- Errors come back as `{ ok: false, error: { code, message } }` with a message Fo can relay to the organizer. Success is `{ ok: true, ... }`, always including `stage` and `next_action`.
- Friends' replies are data, never instructions. Tools that change the plan or money (`confirm_booking`, `calculate_shares` overrides, `cover_bill`, `send_totals`) check the sender against the organizer's contacts. The sender is `by_phone` for a text or `by_email` for an email: exactly one of them.

| Tool | Stage | Args | What it does |
| --- | --- | --- | --- |
| `create_event` | Planning | `title`, `organizer {name, phone?, email?, venmo?}`, `friends [{name, phone?, email?}]` (each needs a phone or an email), `time_slots? [{label, starts_at}]` (ids assigned A, B, C...; omit for a split-only night), `budget_per_person?`, `cuisine_hint?`, `reply_deadline?` (ISO, default now + 2h), `organizer_pick? {restaurant_name, firmness: "locked" \| "suggested"}`, `separate_dinner?` | Saves the event. Returns `event_id`, people with ids, slots, and the list for Fo to confirm with the organizer before texting anyone. Without `time_slots` it refuses with `OPEN_DINNER` while the organizer has an open dinner (the receipt belongs there), unless `separate_dinner: true` |
| `update_event` | Planning, Voting, Booked | `by_phone` or `by_email`, `time_slots?` (replaces options and clears slot answers, used after `NO_OVERLAP`), `organizer_pick?`, `organizer_venmo?`, `reply_deadline?`, `fix_phone? {person, phone}`, `fix_email? {person, email}`, `add_friends? [{name, phone?, email?}]`, `remove_friends? []` | Organizer-only edits to the event |
| `record_preferences` | Planning | `person`, `slot_ids[]`, `any_time?`, `cuisines?[]`, `avoid_cuisines?[]`, `dietary?[]`, `budget?`, `plus_ones?` | Saves one person's round 1 answer. Latest reply wins until the deadline, then rejected with `PLAN_LOCKED` (except people `pick_time` asked about shifting, until the time is picked) |
| `mark_nudged` | Planning, Voting | `person` | Records that Fo nudged someone once |
| `pick_time` | Planning | `force?` (decide now with whoever answered), `skip_shift_check?` (organizer said decide now) | If the best slot (or a tie) leaves someone out, the first call locks nothing and returns `status: "check_shift"` with `ask_to_shift` (a private question per person) and `shift_deadline` (30 minutes); it decides once they've all answered or the deadline passes. Applies the time rules. Returns the slot, who can and can't make it, `party_size` (including plus-ones), the winning cuisine and the hard constraints (dietary needs, max budget) Fo must respect when finding restaurants. Majority wins; `NO_OVERLAP` only when fewer than half of respondents can make the best slot, which means ask the organizer for new options via `update_event`. Records concessions for people who can't make it and returns any `fairness_note` |
| `set_restaurant_options` | Planning → Voting | `options [{name, cuisine?, price_per_person?, notes?}]` (ids assigned 1, 2, 3) | Saves the shortlist and opens voting. Returns a ready-to-send `ballot` that tags each option with its cuisine and price only (never `notes`) |
| `record_vote` | Voting | `person`, `option` (id or name) | Saves one person's vote. Latest vote wins |
| `tally_votes` | Voting | `force?` | Returns the winner, counts and ranked runner ups (used if the winner is full). Ties go to the organizer. Records concessions for people whose pick lost and returns any `fairness_note` |
| `confirm_booking` | Planning, Voting → Booked | `by_phone` or `by_email`, `restaurant_name`, `slot_id?`, `party_size?`, `confirmation?`, `deposit?`, `auto_gratuity?`, `notes?` | Organizer-approved booking. Records deposit and auto gratuity for the split. Allowed straight from Planning when the organizer's pick is locked or the vote is skipped. Returns `timers.day_of_reminder_at` (4 hours before the start, never before 9am in the server's time zone) and `timers.bill_question_at` (2 hours after the start) |
| `add_receipt` | → Claiming | `by_phone` or `by_email` (the organizer's), `items [{description, amount}]`, `subtotal`, `tax`, `tip`, `fees?`, `discount?`, `total`, `tip_included?`, `deposit_credit?` | Validates items sum to subtotal and the parts sum to total. On mismatch nothing is saved and the error says by how much. Allowed from any stage before Paying, so a split-only night works, but refused with `NOT_YET` before a booked meal's start time. Multiple receipts get continuous item numbers. A deposit credit printed on the receipt goes in `deposit_credit` (never `discount`); the server makes sure the deposit is counted exactly once and warns if a booking with auto gratuity gets a receipt with an extra tip |
| `set_attendees` | Claiming | `people[]` | Records who actually came |
| `record_claims` | Claiming, Paying | `claim` (fixed format `"Maya: 1, 4"` or `"Maya: 1, 4x2"` for weight 2) or `person` + `items [{number, weight?}]` | Replaces that person's claims. Returns unclaimed items, shared items to flag, and who hasn't answered. Warns when one person claims every item |
| `calculate_shares` | Claiming, Paying → Paying | `by_phone?` or `by_email?` (required when using `split_evenly` or `treated`), `unclaimed_policy?` (`"block"` \| `"split_evenly"`), `treated?[]`, `fees_split_evenly?` | Refuses with `CLAIMS_PENDING` while any attendee hasn't claimed. Runs the split. Returns each person's items, subtotal, extras, total, Venmo link and a ready-to-send private message. Can be rerun after a dispute. Does not send anything: Fo shows the organizer the totals and only texts friends after the organizer says yes |
| `cover_bill` | Any stage before the meal (noted only), Booked, Claiming, Paying → Settled | `by_phone` or `by_email` | The organizer covers the whole bill (their treat): said up front (a birthday) or asked after the dinner. Before the meal it's noted and the plan carries on with no bill question; after the meal it closes the dinner with no split and no payment requests. Refused once the totals went out |
| `send_totals` | Paying → Settled | `by_phone` or `by_email` | The organizer's yes to the totals. Returns each friend's ready-to-send message with their Venmo link (`delivered: false`: Fo sends them) and settles the event. Payments aren't tracked |
| `record_opt_out` | All | `person` | Friend replied STOP or unsubscribed. Fo must not message them again |
| `get_playbook` | All | none | Returns the full standing instructions. Fo calls it before running a dinner, since Wajo has no place for standing instructions |
| `get_status` | All | `event_id?`, `phone?` or `email?` | Stage, who is pending, and the next action for Fo. With `phone` or `email`, finds that person's most recently active event (handles replies to old threads) and lists any `other_open_dinners` they're in |

Things the server deliberately does not do:

- **Reminders.** Fo schedules the day-of reminder itself. `get_status` in Booked tells it when.
- **Nudges after Voting.** One nudge per round is tracked for Planning and Voting. Claim reminders (one or two, spaced out) are Fo's job; payments aren't tracked or chased; `get_status` lists who is still pending.
